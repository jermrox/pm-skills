### F1 (trace privacy boundaries) - high

> **Trace privacy template still collapses two trust boundaries**
> (`skills/measure-instrumentation-spec/references/TEMPLATE.md:106-114`)
> The skill requires separate minimization decisions before trace egress and before storage, but
> the template provides one `Redaction before storage` field and merely asks whether that mechanism
> runs before egress. A PM can complete the field while allowing raw tenant content to cross into
> an external collector before redaction. The structural fix therefore does not enforce the privacy
> contract described by the skill.
> Recommendation: Add distinct pre-egress and pre-storage rows covering allowed data classes,
> mechanism, owner, and failure behavior. Add QA checks proving raw traces cannot cross either
> boundary when minimization fails.

**Verification: CONFIRMED.** The table carries exactly one row, `Redaction before storage`, whose
bracket text folds the egress question in as a rider: "what is stripped or masked, by what
mechanism, and whether it runs before the trace leaves the process". Egress is therefore a yes/no
appendix to a storage-titled decision rather than a decision with its own mechanism, owner, and
failure behavior. The round-1 fix added the `Data classes captured` row, which was its actual
scope; it did not split the boundary.

### F2 (evaluation sizing) - high

> **Risk-based evaluation sizing remains arbitrary and ungradable**
> (`skills/deliver-prd/references/TEMPLATE.md:140-148`)
> The replacement says to choose a floor per slice but provides no derivation from acceptable
> failure rate, confidence, power, prevalence, or required precision. The Orbit sample simply
> selects 40 or 80 cases and a 25% holdout. Two competent PMs given the same feature would not
> reliably choose the same N, and both could satisfy this template with materially different
> statistical protection. This is the same hand-waving moved from outcome saturation to an
> unexplained risk floor.
> Recommendation: Require a preregistered sizing calculation for measured slices, such as
> acceptable failure rate plus confidence or precision, and a separately justified coverage rule
> for qualitative slices. Grade the derivation in the quality checklist.

**Verification: CONFIRMED ON FACTS, CONTESTABLE ON VERDICT.** The sample numbers are exactly as
cited (`sample_deliver-prd_orbit_ideal.md:311-314`: 40 cases per slice, 80 for one, 25% held out),
and the template gives no derivation rule for the floor. Two points in the template's defence that
Codex does not credit: it explicitly says "A floor is a coverage commitment, not a measurement",
and it requires "If a rate is claimed: state the precision the set supports". So the template does
not claim statistical protection it lacks. The charge is narrower than "it is wrong": it is that a
coverage floor with no derivation rule is unreproducible between PMs. That charge stands.
**This is a design judgment for the maintainer, not a factual error to patch.**

### F3 (release manifest) - medium

> **The new release manifest cannot detect omissions it claims to catch**
> (`docs/internal/release-plans/v2.33.0/skills-manifest.yaml:3-6`)
> The manifest says it turns red when a skill bump disappears or G2 (CHANGELOG preparation) omits
> one. The validator only iterates rows already present, checks directory existence, and treats
> current-version mismatches as warning-only. It never derives changed skills, validates previous
> versions or change types, recomputes summary counts, or reads CHANGELOG.md. The manifest's own
> accounting is also stale: the repository currently has 9 of 44 release folders with manifests,
> with v2.15.0 the latest before v2.33.0, not 8 of 44 with v2.8.0 latest.
> Recommendation: Add an enforcing diff-to-manifest-to-CHANGELOG reconciliation that fails on
> missing or extra rows, wrong current or previous versions, wrong change types, incorrect
> aggregates, and missing CHANGELOG bump entries.

**Verification: CONFIRMED, and the root cause is mechanical.** 9 manifests exist across 44 release
folders (8 pre-existing plus the new v2.33.0 one). The latest before v2.33.0 is **v2.15.0**, not
v2.8.0. The wrong answer is reproducible: `sort` returns `v2.8.0` last because it compares
character by character, while `sort -V` correctly returns `v2.15.0`. The header line is the output
of a lexical sort where a version sort was needed, so v2.10.0, v2.11.0, v2.11.1, v2.12.0 and
v2.15.0 were all skipped. Any future re-derivation of that line repeats the error unless it uses
`sort -V`. The standing restore-or-retire decision is tracked as issue 279 (skills-manifest.yaml:
restore the convention or retire it).

### F4 (Cohere retrieval config) - medium

> **Cohere fix still leaves the retrieval evaluation unreproducible**
> (`library/skill-output-samples/develop-adr/sample_develop-adr_brainshelf_topic-matching-model.md:105`)
> The corrected identifier and 1024 dimensions are valid, but the sample evaluates
> query-to-archive pairs while specifying only `input_type=search_document`. Cohere v3 requires
> `search_query` for query embeddings and `search_document` for stored document embeddings.
> Omitting the query-side setting leaves the reported comparison unreproducible and can change
> retrieval scores.
> Recommendation: Specify `input_type=search_query` for the query side and
> `input_type=search_document` for archive items in the prompt, evaluation description, and Model
> Choice row. Record any truncation and embedding-type settings needed to reproduce the comparison.

**Verification: CONFIRMED, including against live vendor docs.** `search_document` appears exactly
once in the file (line 105) and `search_query` appears nowhere, in a sample whose stated metric is
top-10 recall over query-to-archive pairs. Checked against current Cohere Python SDK documentation
via Context7: `input_type` takes `search_document` for indexed content and `search_query` for user
search terms, and the docs describe the parameter as "critical for optimizing relevance in search
and analysis tasks". Round 1 fixed the model identifier; the query-side setting was never in round
1 scope.

### F5 (sample contract provenance) - medium

> **Retyped Orbit samples encode contradictory contract provenance**
> (`library/skill-output-samples/deliver-prd/sample_deliver-prd_orbit_ideal.md:3-24`)
> The sample now claims deliver-prd 3.0.0 while retaining repo version 2.5.0 and a February
> creation date, then states that the 3.0.0 section was added in August. The sample-authoring
> contract defines repo_version and skill_version as the versions when authored, so this tuple
> cannot identify either the original or maintained contract vintage. The same sweep left the
> parked artifact-provenance spec calling never-shipped deliver-prd 2.3.0 current.
> Recommendation: Represent original and maintained-against versions separately, add an update
> timestamp or sample-content revision, apply the same correction to both Orbit samples, and
> replace all remaining deliver-prd 2.3.0 current-version examples.

**Verification: CONFIRMED on both halves.** Both orbit samples carry `repo_version: "2.5.0"`,
`skill_version: "3.0.0"`, `created: 2026-02-20`. The contract at
`library/skill-output-samples/SAMPLE_CREATION.md:78-79` defines field 5 as "pm-skills version when
sample was authored" and field 6 as "Skill version when sample was authored", so the tuple is
internally impossible: `deliver-prd` 3.0.0 ships with repo v2.33.0, never with v2.5.0. Second half
also confirmed: `_unreleased/fable-innovations/X-03-artifact-provenance-upgrade.md` lines 30 and 88
cite `deliver-prd@2.3.0` as the current version, and 2.3.0 was retyped to 3.0.0 before shipping, so
it names a version that never existed.

### F6 (sample aggregate) - medium

> **Sample aggregate was only partially re-derived**
> (`library/skill-output-samples/README_SAMPLES.md:24-58`)
> The headline says 213 samples, but its listed release cohorts total 210. The later arithmetic
> still reports 209 itemized samples because it omits the new Model Choice sample. The correct
> disk total passes because `check-sample-counts.mjs` validates only headline fields, leaving the
> explanatory aggregate contradictory immediately after the count-fix commit.
> Recommendation: Generate the full cohort decomposition from sample metadata, or remove the
> hand-maintained arithmetic. Extend the count validator if the decomposition remains a release
> claim.

**Verification: CONFIRMED, with one attribution nuance.** Three totals disagree: the cohort
parenthetical sums to 210, the trailing itemized line sums to 209, and disk holds 213 across 63
skills. The **new** regression from `05c0e149` is the trailing line: it was not incremented for the
Model Choice sample and should read 210. The 3-sample gap between the decomposition and disk is
pre-existing and is acknowledged in the file ("a few older samples predate this itemized
breakdown"), so it is not new damage, but it does mean the parenthetical has never summed to its
own stated total. `check-sample-counts.mjs` validates the headline field only, which is why the
count-fix commit passed CI while leaving the prose self-contradictory.

## Operational note for the wrap discipline

The Codex companion job store is session-scoped, not durable per repository. A background review
launched near the end of a session is lost when that session ends: `codex-companion.mjs status
--all` reported "No jobs recorded yet" for this repo despite a round-2 run having been launched on
2026-08-21. Either finish a review in-session or expect to re-run it.
